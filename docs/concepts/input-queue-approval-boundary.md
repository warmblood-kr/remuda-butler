# Input queue vs approvals: current boundary and open decision

Finding (main 55861db): approval-pending requests are NOT in the input queue. The queue (`input_queue.lua`, ledger `input-queue.json`) is fed only by `owner_input.lua`: `accept_prepared` (needs `rec.status=='approved'`, line 86) and `accept_line` (live authenticated owner `!` line, line 119). A pending `approve_text` request lives only in the relay approval store (`attached.state.approvals`, `approval.request` in `approval.lua`, status `open`), persisted by the relay, which survives restarts. Deny/expire call handlers that only reply; neither enqueues. A guard_action approval (e.g. an AWS-login prompt) is a separate kind and never touches the queue.

Flow: `approve-text request` -> `approve_text.request` -> `approval.request` (open, Matrix post) -> owner reaction/reply -> `approval.answer` (`approved`, persisted) -> `apply_approved` -> handler `approve` -> `owner_input.accept_prepared` -> `store:accept` (queued, idempotent by stable `iq-` id derived from event_id+nonce) -> `approval.persist_queue_state` marks the record `queued`. Terminal `remuda butler approve` is refused for approve_text. A second approve gets "Already answered" and a replayed accept returns the existing receipt (duplicate), so approval enqueues exactly once, also across restart.

So requirement 1 already holds structurally. What blocks later input is an already-approved item at the head: `queue:begin` returns `head_blocked` while any earlier same-stream record is non-final, and a post-intent ambiguous result (late/unverified/false/throw, restart during dispatch, marker failure) sets `uncertain`, which only `input-queue resolve ID not_sent|delivered` releases. `uncertain` never auto-retries (it may already have typed text). Approved-but-not-yet-typeable items are also `queued`, with backoff `retry_at`.

Why not shrink it further: moving approved items out of the queue until typeable would not remove uncertain heads, and letting later input pass an uncertain head can concatenate onto text already in the composer. Core is not involved: queue and approval are Butler Lua; only the bound-input provider is core.

Owner decision needed: should an `uncertain` head (a) stay blocking until `resolve` (current, safe), (b) auto-resolve after a window, or (c) release only the stream's later items while keeping the head listed? (b)/(c) weaken the no-replay guarantee. Also whether `input-queue status` should be surfaced when a head is uncertain (a notice to the owner with the `resolve` command), which is the cheapest fix for the "everything stalls silently" symptom.
